# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**F1 Coach** (npm name `box-box`; formerly "Box, Box") — an AI race engineer for EA SPORTS F1 25/26. It reads the game's live UDP telemetry, compares laps against reference traces, drives a force-feedback wheel, and coaches the driver over "team radio" (rule-engine calls in-corner, an LLM analyst between laps, voice in/out). Drivers can publish a lap to an online leaderboard and download other drivers' laps to use as their reference. Tauri 2 (Rust) shell + React 18 / Vite frontend.

Windows desktop is the primary target; **there is also an Android build** (same Rust core, same React app, minus three features — see Android below). The game itself is a PC/console title, so the phone is a second screen on the same network, not a host.

## Commands

```bash

node scripts/fetch-kokoro-model.mjs      # one-time: Kokoro TTS weights (~97 MB, gitignored)
npm run tauri:dev                        # full native app (Rust core owns the UDP listener)
npm run dev                              # web UI only in a browser — no Rust core, no telemetry/FFB
npm run tauri:build                      # release build + NSIS installer

npx tauri android dev                    # Android: build + install + run on a device/emulator
npx tauri android build                  # Android: release APK/AAB
npm run dev:android                      # browser dev server WITH the Android build flags on

node scripts/sync-leaderboard-shared.mjs                            # ALWAYS run before the next line
npx supabase functions deploy <name> --project-ref <ref> --no-verify-jwt
```

- No game running? Set `F1_FAKE=1` (or the Settings toggle) — the Rust core replays a real recorded 25-lap race (`src-tauri/demo/session.json`).
- Rust-only iteration: `cargo check` in `src-tauri/`. First compile is slow: SDL2 is built from source and statically linked (needs CMake + MSVC, both installed).
- **Iterating on the PHONE layout does not need a device or the Android toolchain.** `npm run dev` at a phone-width viewport hits every responsive branch — `useViewport` reads `window.innerWidth`, and the CSS custom properties are plain `@media`. For the compile-time `isAndroid` branches too (no FFB tab, no OpenRouter card, no Calibrator, the platform-voice panel), `npm run dev:android` sets `TAURI_ENV_PLATFORM=android` for a plain browser server on port 1431 — layout and build flags, but still no Rust side, so telemetry and the f1android plugin report themselves unavailable. `src-tauri/gen/android/` is committed, so no `tauri android init` is needed; `cargo check --target aarch64-linux-android` checks the core without a full build.
- **Anything that needs the plugin needs a real Android runtime — but not a real phone.** The emulator AVD works, and a debug build's WebView is inspectable: `adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`, then `curl localhost:9222/json` for the page's socket and a CDP `Runtime.evaluate` (`awaitPromise: true`) calls `window.__TAURI_INTERNALS__.invoke("plugin:f1android|…")` straight from the page. That is how the deferred-resolve contract below was measured without driving the UI.
- Build outputs: `src-tauri/target/release/boxbox.exe` (binary name is fixed by `[[bin]]` in `Cargo.toml`) and the installer `src-tauri/target/release/bundle/nsis/F1 Coach_<version>_x64-setup.exe` (named after `productName`).
- **No JS tests and no linter configured** (the Rust core has unit tests: `cargo test --lib` in `src-tauri/`). Verify frontend changes by running the app — demo mode covers most UI/telemetry paths.
- One-time dev scripts: `scripts/make-demo-session.mjs` (rebuilds `src-tauri/demo/session.json`, the demo-mode replay, from a session export out of the app's own lap log — see Demo mode below), `scripts/fetch-tracks.mjs` (regenerates committed `public/tracks/` geometry from the f1-circuits GeoJSON — all 25 circuits, current layouts), `scripts/fit-corners.mjs` (re-measures each circuit's corner apexes into `apexes` — detects on a chord rebuilt from the same source, so it's safe to run after fetch-tracks and reproduces the committed apexes exactly; see Corner apexes below), `scripts/lib/f1circuits.mjs` (shared source-access — the id→slug map + projection both track scripts must agree on; not runnable), `scripts/fetch-fonts.mjs` (re-vendors the committed `public/fonts/` woff2 + `fonts.css` from Google Fonts — run it only to change the family/weight set), `scripts/make-fixture-lap.mjs` (synthetic trace JSON to exercise track-fitting without driving — output is dev-only, do not commit), `scripts/calibrate-leaderboard.mjs` (measures how well a lap's own trace reconstructs its recorded time, so the leaderboard validator's thresholds are set from data — takes a "Save Session" export, defaults to the demo session).
- `scripts/sync-leaderboard-shared.mjs` is **not** one-time: it copies the pure leaderboard modules into `supabase/functions/_shared/` (gitignored, layout preserved so no import is rewritten) so an Edge Function validates with byte-identical copies of what the app runs. Run it before every function deploy or you ship stale validation logic.
- `node scripts/check-tcam-camera.mjs` asserts that the T-Cam's three.js camera is the *same* camera as its 2D projection, to sub-pixel agreement. Pure math — three needs no WebGL for `Matrix4`/`PerspectiveCamera`, so it runs in plain node. The closest thing to a JS test in this repo; run it after touching either.
- The T-Cam's car assets are **baked from a model, not hand-authored**. `scripts/render-tcam-ego.py` drives headless Blender over `public/Car Models/Formula 2 Car High Poly.blend` and writes all three: `public/tcam-ego.png` (your own car, as seen from the onboard camera), `public/tcam-ego-mask.png` (which of those pixels are bodywork) and `public/tcam-car.glb` (the ghost car). **Blender is not on PATH** — it's the Steam build at `F:\Programs\Steam\steamapps\common\Blender\blender.exe`. Re-run it after ANY change to `CAM_HEIGHT`/`CAM_SETBACK`/`CAM_PITCH`/`FOV_H`/`FOV_V_MAX` in `lib/tcamProjection.js`, or the overlay stops sitting on the road:


## Architecture

### Rust core (`src-tauri/src/`) — real-time work lives here, not in JS
Everything real-time is in-process Rust (an earlier Node sidecar bridge was deleted; ignore any references to it):

- `telemetry/` — single UDP listener on port 20777 parsing the game's **2026-format packets only**. Publishes a lock-free snapshot (`arc-swap`) shared by two consumers.
- `ffb/` — force-feedback engine thread; reads the shared snapshot at full rate and outputs to the wheel via SDL2 haptics.
- `telemetry/demo.rs` — demo mode. Instead of synthesising telemetry it **replays a real recorded session** (`demo/session.json`, ~2 MB, `include_str!`-compiled so a fresh install needs no side files): 25 laps at Singapore, dry mediums into a wet intermediate stint. The file is distance-binned every 10 m with a precomputed time axis, so a tick is a lerp between two bins and each lap comes out at the time it was really set. Only the channels a lap recording can't carry are modelled — forces/slips (from the measured lateral/longitudinal g), ERS state of charge, rpm, tyre wear.
- `lib.rs` — Tauri commands (`set_udp_port`, `set_fake_mode`, `get_local_ips`, `get_ffb_*`/`set_ffb_*`) plus an emitter thread that samples shared state at ~30 Hz and emits Tauri events **only when the `Arc` pointer changed**: `telemetry`, `core_status`, `ffb_gauges`, `ffb_status`. UI event cadence never affects FFB latency.

### Frontend (`src/`)
- `BoxBoxApp.jsx` (~2,700 lines) is the root and deliberate orchestration hub: all telemetry/lap/coaching state, the lap recorder, and the speech-output pipeline live here; screens under `components/screens/` are mostly presentational and receive props from it.
- Hooks wrap the Tauri boundary: `useTelemetry`/`useTauriEvents` (events in), `useFfbEngine` (FFB commands/gauges), `useLlmHealth`, `useUpdateCheck`.
- `lib/env.js` exports `inTauri`; every `invoke()` is guarded with it so plain `npm run dev` in a browser doesn't throw. Keep that pattern for any new Tauri call. It also exports `isAndroid` — see Android below. **`inTauri` is no longer the right test for "desktop"**: Android IS Tauri, it just doesn't register the FFB commands.
- Laps recorded while demo mode is on are stamped `source: "demo"` by the recorder and kept off every board by `isDemoLap` (`lib/driverStats.js`) — a replay carries real lap times, so without that it would take personal bests. Demo and driven laps are two separate worlds: `computeDriverStats(laps, { demo })` picks a side (default = the driver's own), the Live screen's record buckets key on it, and the coach's `trackLaps` pool only ever holds one of them. Demo laps also can never be published online — which means **the upload path can't be exercised in demo mode**; test it against real laps already in IndexedDB.
- A recorded lap's `meta` carries `trackId`, `trackSlug` and `trackLengthM` alongside the display name. Laps recorded before those existed still resolve their circuit via `getTrackByName(meta.track)`, so the whole back history stays publishable — resolve lazily at read time, never bulk-migrate at boot.
- Persistence is IndexedDB `f1coach` **v4** (`lib/lapStore.js`): `laps`, `avatars`, `trackmaps`, `reftraces`. Every `onupgradeneeded` branch is guarded by a `contains()` check, so a version bump is a pure addition — **don't rewrite it into an `oldVersion` ladder**. Any new driver-keyed store must also be re-keyed in `renameDriver`, or a profile rename silently orphans it.

### Android build, and the responsive split
Same Rust core (FFB `#[cfg(desktop)]`-ed out — SDL2 is built from C and can't cross-compile) and the same React app. `src-tauri/gen/android/` is committed.

- **`isAndroid` (`lib/env.js`) is a BUILD-TIME constant**, `__IS_ANDROID__` from `vite.config.js` off Tauri's `TAURI_ENV_PLATFORM` — not a user-agent sniff. That's what lets Rollup fold the branches and drop the excluded code rather than ship it unreachable. `TAURI_ENV_PLATFORM` is unset outside a Tauri build, so a plain `npm run dev`/`npm run build` is always the "desktop" build — the Android-only omissions can't be reproduced in a browser at any width.
- **Three features are compiled out on Android**: FFB (no wheel, and the Rust commands don't exist — `useFfbEngine` gates on `inTauri && !isAndroid`, stays mounted, goes quiet), the OpenRouter analyst and its API-key UI (the deterministic rule-engine coach and the Coach tab stay), and the Trace Calibrator (raw mouse drag/resize on thin edge hit-areas).
- `src-tauri/gen/android/` is committed and re-running `tauri android init` does NOT clobber hand edits there (checked). Everything under `app/src/main/java/com/boxbox/app/generated/` is auto-generated and says so; `MainActivity.kt` beside it is ours, and is where the hardware back button is claimed (see Touch input below).
- **Kokoro is reached only through `lib/tts/` (`index.js` façade + `voices.js` + `kokoroStub.js`)** and never imported directly. Vite's worker handling is EAGER: merely transforming a module containing `new Worker(new URL(...))` emits the worker chunk plus kokoro-js, `@huggingface/transformers` and their own bundled 21.6 MB ORT wasm — a dead `if (false)` does not prevent it (measured: dist stayed at 30 MB). So the real client is swapped for the stub by a resolve **alias** on Android and gated behind `__HAS_KOKORO__` elsewhere; `stripVoiceAssets` then deletes `dist/kokoro` and `dist/ort`, which `public/` copying would otherwise smuggle in. ~6 MB instead of ~30. Android speaks through the platform TTS instead (below). `isKokoroLoaded()` must stay SYNCHRONOUS — the speech arbiter calls it inside a render path.
- **`tauri-plugin-f1android/` is the Android bridge** — a real plugin crate (Rust commands + a Kotlin Gradle library under `android/`), not app code, because a `@TauriPlugin` class has to live in a library project Gradle can include. Three concerns, all of them WebView capability gaps rather than features: platform text-to-speech, `FLAG_KEEP_SCREEN_ON` (`navigator.wakeLock` needs a secure context and `http://tauri.localhost` isn't one), and the Wi-Fi multicast lock (only broadcast telemetry needs it; unicast to the phone's own IP is never filtered). Wiring worth knowing: `links = "tauri-plugin-f1android"` in its `Cargo.toml` is REQUIRED — that is what publishes `android/` into the generated `gen/android/tauri.settings.gradle`; the Kotlin package must equal the `PLUGIN_IDENTIFIER` the Rust side registers, since the class is resolved as `<identifier>.<class>` by reflection; and the permission lives in its own `capabilities/android.json` with `"platforms": ["android"]`, because naming `f1android:default` in the shared default capability would fail the desktop build. (`permissions/autogenerated/` is written by `build.rs` from the `COMMANDS` list and IS committed, so a capability resolves without a build first. The crate was hand-written rather than scaffolded — `tauri plugin new` prompts and dies without a TTY, so it can't run from a non-interactive shell; the installed `tauri-plugin-dialog` in the cargo registry is the reference layout.)
- **`speak` resolves when the phrase ENDS, not when it starts.** The Kotlin side parks the `Invoke` and settles it from `UtteranceProgressListener` (done, error and interrupted all resolve — the caller only needs to know the queue may advance), and the Rust command is `async` + `run_mobile_plugin_async`, so the wait is a suspended future rather than a blocked thread. That is what lets the arbiter treat all three engines identically: one `onDone` per phrase, whoever spoke it. Measured on the API-34 emulator (3.4 s for a corner call, 1.2 s for "Lift and coast") and **confirmed on real hardware** — a Xiaomi on Android 15 answers `ready` with 28 offline English voices, speaks the same corner call in 3.9 s, and settles a preempted call when `stop` lands. What still hasn't been *heard* is the rule engine's own spoken corner call: demo mode replays a race with no reference loaded, and `refMatch` correctly mutes it there. The alternative — resolve on start, emit a completion event — needs a Channel and a correlation table in JS to answer the same question.
- The JS side is `lib/tts/native.js` (re-exported through the same `lib/tts/` façade, so the app still has ONE import point for speech) plus `lib/androidBridge.js` and `hooks/useAndroidDevice.js` for the two device concerns. Readiness is POLLED, not pushed: `is_ready` for up to 8 s, then a definite answer either way — a device with no voice data installed reports that, and the Settings voice panel says so rather than going quiet. Voices needing a network round trip are filtered out plugin-side; this app is built to work offline at a race weekend.
- **Responsive work is split by mechanism, and the split is load-bearing.** STRUCTURE (nav becoming a bottom tab bar, modals becoming sheets, a row becoming a column) goes through `hooks/useViewport.jsx` — one provider, so a rotation is one state change at the root rather than 20 `matchMedia` listeners. Pure SIZING (grid columns, font sizes, tap targets) goes through CSS custom properties in `index.html`'s `:root` with real `@media` blocks, which cost no re-render: `--col-min`, `--grid-live-tiles`, `--grid-live-sectors`, `--grid-board-row`, `--screen-px`, `--tap`. **The catch both ways is the cascade**: an inline literal beats a stylesheet rule, so a site must actually read `var(--x)` before a media query can bite — and conversely `@media (pointer: coarse)` gives every button/select/range a `min-height: var(--tap)` (44px on a phone), which only an INLINE `minHeight` can override. Several phone controls that are a line of text rather than a target do exactly that on purpose (the studio's channel chips, the S1/S2/S3 strip, the zoom slider, the lap-selector rows).
- **The phone layout is not the desktop one at a smaller size.** Where a desktop panel parks controls in the corners of a viewport, the phone build generally hoists them into rows above and below it — see Driving Lines below. Anything defined once and placed twice should stay that way; don't fork a phone copy that then drifts.
- Two smaller traps, both already paid for: `index.html`'s viewport meta sets `maximum-scale=1, user-scalable=no` plus `touch-action: manipulation` (without them the WebView's double-tap/pinch zoom fires on ordinary taps and drags, and every control pays a ~300 ms tap delay); and hiding a grid cell via the `.lb-secondary` class fails if that cell carries an inline `display`, which is why the leaderboard row drops its detail cells outright on phone rather than relying on the stylesheet.

### Touch input, and the two gestures that had to be invented
The layout fitting on a phone is not the same as the screens being usable with a finger; these are the mechanisms that close that gap.

- **`touch-action` is a POLICY decision per surface, and the two answers are both right.** `none` on the 28px playhead scrubber, where a drag can only ever have meant the playhead. `pan-y` on the trace stack and the Driving Lines map, which fill most of a phone — there a horizontal drag is the app's (scrub, pinch) and a vertical one still scrolls the page. `none` on a full-height panel traps the screen behind it, which is how a panel ends up unscrollable on a device nobody tested.
- **The trace stack's tap and its scrub are the same gesture, told apart by distance and time** (8px / 250ms in `TelemetryStudio`), because the whole stack is both the play/pause target and the read-out surface. Two consequences worth keeping: the press seeds the read-out (a tap-and-hold answers immediately instead of waiting for a move a finger may never make), and a press that lands on a `button` inside the stack is never a candidate tap — the sector buttons' `stopPropagation` on `click` cannot stop a `pointerup` that has already bubbled.
- **A finger lifting is not a mouse leaving.** `pointerleave` clears the read-out only for `pointerType === "mouse"`; on touch the lift is the moment the driver reads the number they scrubbed to, so the chip stays until the next press.
- **Pinch feeds the SAME zoom state as the wheel and the slider** in both whole-scene views — a `Map` of live pointers, gap ratio into `zoomBy` (3D) or `setZoom` (map). Lifting one finger out of a pinch re-seats the orbit drag on the remaining pointer, or the camera jumps by the gap between them. Double-TAP resets the 3D camera and is counted by hand, since `touch-action: none` means the WebView synthesises no `dblclick`.
- **`components/Hint.jsx` is the tooltip policy, not just a component.** Fine pointer keeps the native `title`; coarse taps to a bubble. Only INFORMATIONAL titles on non-interactive elements are converted (why a lap is struck through, tyre age/wear, what call lead does) — a tooltip reading "Zoom in" over a `+` button is not content, a wrapper around a button eats its click, and a **disabled** button swallows the event before any wrapper sees it (so disabled-reason tooltips need visible text instead, and remain a gap). The bubble is portalled to `<body>` with viewport coordinates because these live inside lap rows and overlay cards that clip their overflow, and it is `pointer-events: none` so it can't steal the tap meant for what it covers.
- **The hardware back button had to be claimed in Kotlin.** `TauriActivity` sets `handleBackNavigation = false` (one page, no history to walk), so back hit the platform default and destroyed the activity — measured, two `pushState` entries deep, process gone. `MainActivity.kt` now asks the page via `evaluateJavascript`, whose callback carries the value, and treats anything but a literal `"true"` — including the `"null"` a wedged page returns — as unhandled, so back can never become a dead key. `hooks/useAndroidBack.js` holds the layer stack: modals register on mount, `BoxBoxApp` registers the outermost layer that walks out to the Dashboard first, and the handler is held in a REF so an inline arrow doesn't re-register (and re-order the stack) on every render of a 30 Hz screen.
- **Two things about verifying any of this.** The emulator reports `(hover: none)` true but `(pointer: coarse)` **false** — it is mouse-driven — so the 44px tap floor in `index.html` does not apply there and cannot be checked on it. And a Xiaomi device refuses `adb shell input` without the extra "USB debugging (Security settings)" permission, so gesture testing goes on the emulator while the phone is for what CDP can drive.

### Files in and out of the Android build
Saving and loading both work, but neither works the way the desktop build's does, and the failure modes are unintuitive enough to be worth writing down.

- **`save()` from `tauri-plugin-dialog` IS supported on Android** (the plan doubted it): it opens the system document picker and resolves `null` on cancel, which is what `saveJson` already treats as cancelled. What it resolves WITH is a SAF `content://` URI, not a path — so `write_text_file` (a plain `std::fs::write`) cannot open it. That handle goes to `f1android|write_document` instead, which writes through the ContentResolver. One branch in `saveJson` covers every JSON export, since they all funnel through it.
- **An anchor download is INERT in a Tauri WebView** — no download manager is wired to it. That is invisible on desktop (WebView2 has one) but on Android it made the track-map PNG button do nothing at all. `saveBlob` routes it through the same dialog, base64 over the IPC bridge because that bridge carries strings.
- **A just-saved file re-imported from Android's "Recent" list arrives EMPTY.** The Save picker creates the document at zero length and our write fills it afterwards, so the Recent entry keeps the length it was created with; Chromium sizes the `File` from that and `FileReader` returns "". Measured: the picker reported 0 bytes for a file that was 167,206 bytes of valid JSON on disk, with MediaStore agreeing. Opening the same file from ☰ ▸ Downloads reads it in full. Nothing in the app can refresh that entry, so `readPickedText` (shared by trace, session and profile import) catches a zero-length pick and says which menu to use instead — the previous message blamed the file, which reads like the lap was destroyed.

### Android distribution
- **The launcher icon has to be copied into `gen/android` by hand.** `tauri icon` writes `src-tauri/icons/android/`, but nothing syncs that into the committed `gen/` tree, so builds shipped the **Tauri** logo until the densities were copied across. There is deliberately no `mipmap-anydpi-v26`: the generated foreground is full-bleed, and an adaptive icon masks its foreground to the inner ~66 of 108dp, so a round mask would crop the wordmark. A real adaptive icon needs a foreground drawn with safe-zone margin.
- **`windowBackground` is why the app doesn't flash white.** The launch window is painted by the theme from activity creation until the WebView paints, and the platform default is white; `values/`, `values-night/` and `values-v31/` (the Android 12+ splash) all paint `@color/app_background`, which has to be kept in step with `index.html`'s `bg` by hand.
- **Release signing is wired but keyless.** `signingConfigs` reads `app/keystore.properties` if present; without it the release APK is simply unsigned, because a clone has no keystore and must still build. That file and any `.jks` are gitignored — the keystore IS the app's identity, and losing it means every installed copy must be uninstalled before an update will apply. Creation steps sit in `app/build.gradle.kts` beside the config that reads them.
- **Sideloading is the distribution channel**, and the update check now enforces that: on Android it stays silent unless the GitHub release carries an `.apk`, and links at the asset. Publishing an APK asset is what turns that path on. Play Store publication remains a separate question, gated on asset provenance rather than on anything technical — see the T-Cam model licence and the team-logo trademarks in Gotchas.
- **Auto-backup is off** (`android:allowBackup="false"`): it would try to copy the WebView data dir — the whole lap history, in IndexedDB — under a 25 MB quota, and fail silently past that. Settings ▸ Driver Profile ▸ Export Profile is the backup the driver controls.

### The four camera modes of Driving Lines
Analytics ▸ Driving Lines draws ONE scene — road, both racing lines, both cars, corner markers — from four cameras, picked by the pills at the top of the viewport. On desktop every overlay (delta, segment card, mini-map, zoom) is an absolutely-positioned sibling of the viewport, so a mode swaps only what's underneath them.

**On a phone those overlays are ordinary rows instead.** The viewport there is ~355px wide and the same four boxes covered the road and each other. Each cluster is therefore defined ONCE and placed twice — `camPills`, `deltaBox`/`legend`, `segCard`/`segInner`, `zoomBar`/`zoomControls`, `transport` — absolute on desktop, stacked rows on phone (where zoom, key and segment read-out share one box). Consequences worth knowing: the **mini-map is not built at all** on a phone (`mini` returns null, so its path build is skipped too — a 150×104 inset hides the thing it annotates); the scrubber gets a line of its own (sharing one left it ~120px for a whole lap); the Segments/Sectors toggle and the ‹ › steppers are desktop-only, since the scrubber already moves the playhead; and the map viewport is `flex: 1 1 0` there so it absorbs whatever the rows leave in a fixed-height card, rather than pushing them out of it.

- **Map** — top-down SVG. Geometry is fixed and only the viewBox moves, so the DOM is built once.
- **3D** — free orbit camera (`TrackOrbitView.jsx` + `lib/orbitScene.js`), see below.
- **T-Cam / Compare** — the onboard views, one seat or two stacked (`TrackCamView.jsx` + the tcam modules).

`DrivingLinesView` calls the last two `onboard`; several overlays key on that rather than on `camMode !== "map"`, because 3D is a whole-scene view and shares the map's wording and its **zoom slider** (a viewBox there, a camera distance here — the mouse wheel writes the same state, so the slider tracks a scroll).

### T-Cam onboard view (`lib/tcamProjection.js`, `lib/tcamScene.js`, `lib/tcamCarLayer.js`)
Analytics ▸ Driving Lines ▸ T-Cam — a first-person camera riding a recorded lap.

- `tcamProjection.js` is a hand-written pinhole camera with **zero imports**: pure arithmetic on plain numbers, so it can be reasoned about and checked in node without a canvas anywhere near it. Its camera constants are shared by the live road AND by the Blender bake — they are not private tuning knobs.
- `tcamScene.js` paints the world into 2D canvas in a **fixed layer order rather than a depth sort**, because everything it draws sits on one surface and there is no occlusion to resolve.
- **three.js is back** — dropped in f6618fe with the old 3D track scene, re-added 2026-08-04 for exactly one job: the cars (`tcamCarLayer.js`). A car has volume and turns independently of the camera, which a flat decal can't express. It renders to an **offscreen** canvas that `TrackCamView` blits into the 2D context mid-scene, after the ribbons and before the fog. Stacking a transparent canvas over the top instead puts a 200 m-distant car through the haze and out through your own halo. It is dynamically imported, so ~560 kB of three + GLTFLoader never lands in the entry chunk every launch parses.
- Both cars — the ghost *and* your own — are the same `tcam-car.glb` drawn in **one GL pass**, so the depth buffer sorts them against each other. Wheels roll off **ground distance** (`dist / 0.335`), never an integrated speed, so scrubbing or pausing stays correct.
- Everything fails soft. No WebGL, a lost context, or a model that won't load falls back to `tcamScene`'s flat ground decal for the ghost and the baked `tcam-ego.png` + mask for your own car.
- **The ghost FADES at close range rather than being cut.** `resolveOtherCar` used to return null below 8 m, and on a lap within a tenth of the reference the gap crosses that line repeatedly — the car vanished whole and came back a frame later. It now carries an `alpha` that smoothsteps between `FADE_FULL` (12 m) and `FADE_GONE` (3 m, where the rear wing is at the lens), which both painters honour, and the model sits at a base `GHOST_ALPHA` so the fade reads as more of the same rather than a separate effect. The bottom of that ramp is also what keeps POS-SYNC honest: both cars are at the same track distance there, so the ghost is alongside at ~zero depth and falls out at alpha 0, exactly as the old cutoff dropped it. Materials are marked `transparent` once at clone time — it is program state in three, so flipping it mid-run costs a shader recompile, while `opacity` is a free uniform.
- **Everything on the road surface reads its height from `roadYAt`,** which walks to the nearest centerline row and then INTERPOLATES (`rowFracAt` + `elevAt`) exactly as `buildTCamCamera` always did for the eye. Taking `rows[nearest].y` is a step function, and for anything that MOVES that step is visible judder: rows are 2.5 m apart, so a car at racing speed crosses one every 2-3 frames and jumps by the whole height difference — ~0.4 m on Eau Rouge's gradient — while the tarmac beneath it slides smoothly. The ghost, the ribbons and the corner posts all share it: one road surface, one answer.

### Playback: how the cars are placed and timed (`lib/racingLine.js`, `DrivingLinesView.jsx`)
The single hardest thing in this panel to get right, and it took four attempts, so the reasoning is worth keeping. The playhead advances **linearly in lap-distance fraction**, and both cars are placed from it. Making that motion look like driving needs three separate things, and fixing any one alone barely helps.

- **`buildEvenPath` — cars ride an arc-length-even resample of their line, not the spline directly.** Two independent causes made them surge. First, the playhead is parameterised by the game's ODOMETER while a car is drawn at its recorded POSITIONS, and per 10 m bin those disagree by about ±20% (measured p5 0.86, p95 1.10) because the Motion and Lap Data packets aren't sampled at the same instant — so a bin where the odometer says 10 m passed but the positions moved 8.6 forces a crawl, and the next one a sprint. Second, Catmull-Rom evaluated at a `t` running 0→1 per span has a speed that varies WITHIN the span, and spans are 3-13 m apart because the recorder writes one sample per rounded bin wherever the tick landed; that roughly doubles what the odometer left. Together they put ground-covered-per-frame 31% either side of its mean. The resample fixes the second by construction and carries a de-jittered fraction map for the first: **31% → 11%**, worst in-lap single-frame jump ~0.5 m → under 0.05 m. Note the fraction of each dense sample must be assigned linearly in **arc**, not in the spline's own parameter — getting that wrong hands back exactly the variation the resample exists to remove, and reads as "the fix did nothing".
- **The odometer is de-jittered ONLY inside that path.** `distAt` stays exactly as recorded, so ribbons, segment cards, sector maths and the telemetry cursor still address the lap by the number the game gave. The cost is that a car can sit up to ~0.7 m from where the raw odometer would have put it — inside the noise being removed. Re-parameterising `distAt` itself was tried and rejected: the chord sum runs ~50 m short of the odometer over a lap (corner-cutting), and it moved cars 4-5 m mean / 17 m worst, which breaks the "same track distance" premise pos-sync exists for.
- **Pace-sync's curves are read as a monotone cubic, not linearly.** The ghost's speed is the slope of its pace curve, so a piecewise-linear read makes it hold one pace for ~11 frames and change it in a single frame — up to 11 m/s of apparent speed in one frame. Fritsch-Carlson (`monoSlopes`/`monoAt`) makes the slope continuous; monotone-preserving is load-bearing, since an overshoot in a position table is a ghost driving backwards. Worst single-frame step drops ~7×.
- **The time axis is READ when the lap has it.** The recorder stamps the game's own lap clock onto every 10 m bin, and `recordedTimeAxis` prefers it, all-or-nothing so a half-stamped lap can't splice a measured curve onto a derived one. Laps recorded before that fall back to `integratedTimeAxis`, a trapezoid over Δdistance ÷ speed — which runs ~1.9% long and, more visibly, carries order 10 ms of local noise; at Spa's 66 m/s that is two thirds of a metre of phantom gap movement. Pre-filtering the speed channel to hide it was tried and rejected: it WIDENS the lap-to-lap spread of the derived lap time (0.278% → 0.317%) even as it lowers the mean bias, and pace-sync reads the RATIO of two laps' curves, so a shared bias cancels and only the spread survives.

### The car asset (`lib/carModel.js`)
`public/tcam-car.glb`, loaded **once per session** and cloned per car — two views draw cars now, and each parsing its own copy of the same 450 kB of glTF is pure duplication. The lap colour (white = reference, accent/cyan = comparison) is applied to the model's `Body` material alone; that separation is what keeps tyres and suspension black, and it's why a liveried model was rejected. Clones share the template's **geometry** and clone only materials, so an instance's `dispose()` frees materials and never geometry — tearing down one renderer must not pull the model out from under the other view.

### 3D orbit view (`components/TrackOrbitView.jsx`, `lib/orbitScene.js`)
Analytics ▸ Driving Lines ▸ 3D — the map's scene as real geometry, with a camera you drag. Left-drag orbits, the wheel zooms, double-click resets. For seeing how someone else takes a corner from an angle that shows it; the plan view flattens the entry-to-apex sequence and the T-cam can only show it from one of the two seats.

- **Ordinary three.js with a depth buffer**, unlike the other two — the moment the camera is free, a car IS in front of a kerb and the far side of a hairpin is behind the near side. `orbitScene.js` is dynamically imported, so three still stays out of the entry chunk.
- **`ORDER` puts the cars FIRST, ahead of every road marking**, and that is the mechanism behind markings being hidden behind them — not the cars' depth write on its own. A marking drawn *before* a translucent car is already in the colour buffer and blends through it whatever the depth buffer says; drawn after, it is simply rejected. So the sequence is cars → kerbs → edge lines → brake dots → racing lines, which INVERTS `drawTCamFrame`'s — that one can paint the car last precisely because it has no depth buffer to lean on. Everything on the road surface is within centimetres of everything else, so left to the depth sort a brake dot would get to decide it was in front of the car parked on it. Note `renderOrder` is **per object** — setting it on a car's root `Group` does nothing, since a Group is never drawn.
- **The marking lifts are millimetres, and that is load-bearing.** They exist only to stop the markings z-fighting the road, but once a marking is depth-tested against the car rather than painted under it, its height is the height at which it pokes through the bodywork — at a grazing angle a line floating 10 cm up passes in front of a front wing sitting at 5 cm. The logarithmic depth buffer makes 6 mm separations safe at any distance the camera can reach.
- **Kerbs and the dashed reference line are the T-cam's, rebuilt as geometry** — same `KERB_W`/`KERB_K_ON`/`KERB_STRIPE` constants, same "the outer metre of the road on the inside of a corner already IS the kerb" trick off `trackGeometry`'s `EDGE_MARGIN`, and the same world-metre dash walk. Two things had to change: the kerb's curvature fade is **per-vertex** (an RGBA colour attribute, which three reads as vertex alpha) because the whole circuit is one static mesh rather than the few hundred metres in front of a camera; and the dashes are a little longer than the T-cam's 3/4 m because this ribbon is ~4× the width, so at 3 m they came out square.
- **The cars are translucent AND write depth**, which sounds contradictory and isn't: three sorts the transparent queue back to front, so the FAR car is drawn first and the near one blends over it — both are there, and the far one reads through at 1 − `CAR_ALPHA`. Two cars comparing a corner spend most of it on top of each other, and keeping the one behind visible is the whole reason for the alpha. Writing depth is what makes everything else occlude correctly: a car hides the racing line it stands on, its own far side doesn't x-ray through its near side, and a car across the circuit doesn't float through the road in front of it. Only two almost exactly coincident cars sort unstably, and at that point they are one shape anyway.
- **Azimuth is world-fixed**, seeded on first frame (and on reset) from the car's heading so the view opens looking up the road. Car-relative azimuth would swing the corner around as the car turned through it, which is the one thing this view exists to hold still. The camera watches the **driven** car, not the midpoint of the two — in pace-sync the midpoint is empty tarmac between them.
- Static geometry is rebuilt only on an **identity change** of the model/lines/marks (everything upstream is memoised), so the per-frame cost is a reference comparison, not a sweep of a few thousand centerline rows. The scene and that "what I built" record are created together — a new scene starts with an empty world.
- Fails soft the same way: no WebGL renders a note in the viewport, and a model that won't load falls back to a plain wedge that still says where and which way round.

### Coaching — two layers, never let the LLM into the real-time path
- A deterministic rule engine makes in-corner calls (brake, lift-and-coast, ERS) and always runs.
- The LLM (`lib/coach/`) is a **between-lap analyst only** — one debrief call when a lap completes, via **OpenRouter** (cloud-only; a former Ollama path was removed). The chat panel and the on-track one-shot tip that used to sit alongside it are gone. `prompts.js` builds the prompt, `schema.js` validates/repairs the structured reply, `guardrails.js` enforces grounding — the model may only cite numbers present in the lap evidence.
- Neither layer runs when the loaded reference isn't comparable with the lap driven (`lib/coach/refMatch.js`): different circuit, dry vs wet, race vs push lap, or a different compound withholds the insights AND mutes the corner calls, since both are derived from that reference.
- A priority speech arbiter (`urgent > normal > low`) in BoxBoxApp keeps engine calls and AI tips from talking over each other; stale tips are dropped. It drives three engines through one `play()` — Kokoro, Web Speech, and Android's platform TTS — and picks the platform one by AVAILABILITY rather than preference, since on Android it is the only one there.
- Voice out is local ONNX Kokoro TTS (`lib/kokoroTTS.js`, in a worker — see `lib/kokoroWorker.js`), **imported only via the `lib/tts/` façade** (see Android above; importing `kokoroTTS.js` directly re-adds ~24 MB to every bundle). There is no voice input; the Whisper STT stack was removed with the chat.

### Online leaderboards (`lib/leaderboard/`, `supabase/`)
Publishing a lap to a public board and downloading someone else's as a reference. Backed by **Supabase free tier** (Postgres + storage + anonymous auth + Edge Functions) — chosen over Firebase because Firebase requires a paid plan with no hard spending cap just to run functions.

- **A board is `<trackSlug>__<sessionGroup>`** — 50 of them, **Qualifying and Time Trial only**. Race is refused (fuel and tyre management a push lap doesn't carry); Practice is refused because it can be either and the game gives no way to tell, the same reason `refMatch` won't classify it. `lib/sessionGroups.js` holds the shared `SESSION_GROUP` map (Sprint Shootout → Qualifying) — **do not use it directly as the board map**, it also maps the two types boards refuse; `boardKey.js` layers an explicit allow-set on top.
- **Compound is shown, not partitioned on.** But `refMatch` still blocks on it, so a board can hold a Soft and an Inter reference side by side — every row runs `matchReference` to warn before you pick one the coach would then mute.
- **The primary key `(board_id, driver_id)` IS the one-lap-per-driver rule.** An upload is an upsert that only lands when it's faster. There is no rank column — rank is counted, because a stored one is stale the moment anyone else publishes.
- **Clients never write.** No insert/update policy exists anywhere; the only writer is the `submit-lap` Edge Function holding the service role key. That split is structural: a policy can't inflate a gzipped trace and check the speeds in it against the lap time being claimed.
- **Anti-tamper (`validate.js`) and its limit.** Five checks — sector sum (tightest, exact to 20 ms), lap time re-derived from the trace, distance coverage/gaps, ERS monotonicity + ceiling, speed sanity. Catches edited lap times, truncated traces and flashback signatures. **It cannot catch a genuinely-driven lap with assists on** — the game sends those flags, the Rust parser doesn't read them yet. Highest-value follow-up.
- **Thresholds in `limits.js` were measured, not guessed** (`scripts/calibrate-leaderboard.mjs`). Read the comments before touching them: integrating a distance-binned trace runs systematically ~2% HIGH, so the tolerance window is offset rather than centred — a symmetric one rejects nearly every honest lap. Likewise the ERS ceiling is 13 MJ, not 4: 4 MJ is the battery's capacity, not a per-lap deployment limit.
- **Everything fails soft**, following `lib/updateCheck.js` — no call throws, reads resolve to null. Turning the feature off in Settings makes *zero* requests. The screen distinguishes four states (ready / disabled / offline / error) because collapsing them is how a board looks broken at a race weekend.
- Downloaded references persist in IndexedDB (`reftraces` store) so they survive a restart and work offline; they flow into `refTraces` through the same path `loadTrace` uses.

### Telemetry facts that shape the code
- The UDP stream has only **3 real sectors**; the app derives **18 mini-sectors** locally from real sector boundaries (`MINI_SECTORS`/`MINI_PER_SECTOR` in `lib/format.js`). Don't look for mini-sector data in packets — it doesn't exist.
- **A lap's odometer and its world positions do not agree, and the disagreement is not small.** `lapDistance` comes off the Lap Data packet and `worldX/Z` off the Motion packet, and they are not sampled at the same instant, so per 10 m bin the geometric distance between two samples is anywhere from 0.86× to 1.10× the distance the odometer claims passed (measured over the demo laps; worst 0.59×). Neither channel is wrong — they are out of phase. Anything that parameterises by one and draws with the other has to reconcile them or it will visibly stutter; see the playback section above for how, and for the reasons re-parameterising `distAt` wholesale is not the answer.
- **The recorder samples are 10 m BINS, not 10 m apart.** `buf.bins.set(Math.round(lapDistance / 10), bin)` keys by the rounded bin but stores whatever distance the tick actually carried, so real spacing runs 3-13 m. Anything that assumes even spacing (spline parameterisation, per-sample smoothing windows, "±N samples ≈ ±N×10 m") is approximating.
- **Every bin carries the game's own lap clock** (`bin.t`, from `lapTime`) as of v4. Prefer it over reconstructing time from Δdistance ÷ speed — that integral runs ~1.9% long and carries order 10 ms of local noise. Laps recorded before v4 have no `t`, so readers must guard and fall back rather than assume.
- Track geometry (`public/tracks/`) is committed data; runtime alignment into the game's world frame happens in `lib/trackGeometry.js`.
- **The shipped geometry is much denser than its source, and interpolating that gap is a spline's job, not a lerp's.** The upstream f1-circuits ways carry only 84-160 vertices per circuit (20-60 m apart on average, 8 m through a hairpin and 860 m down the Las Vegas Strip); `public/tracks/*.json` resamples them to a point every 2.5 m. Resampling LINEARLY — which is what the first version did — puts every added point on a chord, so the files look dense while their shape stays a polygon: 600+ rows per lap turning under 0.05° with the odd one turning 56° in a single step. Nothing in the plan view showed it; the T-cam draws a corner from the seat and it arrived as flat panels. `fetch-tracks.mjs` now resamples along the same centripetal Catmull-Rom the drawn lines use (imported from `lib/racingLine.js`, not re-typed), and `trackGeometry.finishModel` runs a Savitzky-Golay pass (`deFacet`) over every model on load to take out what a 20-60 m survey can't resolve — that one also covers the heuristic fallback road, which is built from 10 m lap samples and has the same problem.
- **Corner positions are not lap fractions in the data.** Each track file's `apexes` are fractions of that centerline's own arc length from point 0 — and point 0 is wherever the upstream GeoJSON way started (the start/finish line at Monza, ~845 m past it at Monaco), with file order not always the racing direction (Singapore's is traced backwards). `trackGeometry` recovers both when it fits a lap (`reverse`, `sfFrac`), `lib/cornerAnchors.js` caches them per circuit and does the numbering, and `hooks/useTrackCorners.js` hands the rest of the app `{ n, name, f }` with `f` as a real lap fraction. Don't hand-write lap fractions.
- **`fit-corners.mjs` detects on the CHORD, not on the shipped spline — that separation is deliberate and load-bearing.** The detector calls a point "turning" by its per-point heading change, which needs straights to be *exactly* straight. That holds on a linear resample of the source (all curvature sits at the sparse surveyed vertices) but not on the spline, which smears each vertex's wobble across the straight between vertices until it clears the floor — detecting there put 42 of 424 apexes >25 m wrong and no threshold fixed it. So the script rebuilds the chord from the same source (at the committed 2-decimal precision, or a corner sitting exactly on the floor flips on sub-cm noise), detects on that, and writes the fractions into the spline file. It reproduces the committed apexes byte-for-byte, so `fetch-tracks` then `fit-corners` is a clean no-op; the ~0.6 m mean (2.5 m worst) gap between a chord fraction and the spline it's drawn on is the same gap the road moved when it was smoothed. The `FORCED`/`EXCLUDED` tables stay in the chord frame they were authored in.

### Theming
Team "livery" skins recolour the whole app via CSS variables set on `<html>` (`lib/ui/skins.js`). UI colour tokens (`C` in `lib/ui/tokens.js`) are var()-backed and skinnable; **data-meaning colours (tyre compounds, flags, ERS modes) stay fixed** — don't route those through skin vars.

## Gotchas

- **CSP is strict** (`tauri.conf.json`): any new external endpoint must be added to `connect-src` in **both `csp` and `devCsp`** or it silently fails in the packaged exe while working in `npm run dev`. This is why ONNX runtime wasm is self-hosted in `public/ort/` (copied by `scripts/copy-ort.mjs` on predev/prebuild) instead of ORT's default jsdelivr CDN. Note `tauri dev` enforces `devCsp` (dev is NOT CSP-free): it deliberately allows `cdn.jsdelivr.net` because the self-hosted `/ort/` path is PROD-only (Vite's dev server can't serve `public/` files as module imports), so dev voice falls back to the CDN. The Supabase origin needs only ONE entry — REST, auth, storage and functions are all paths on the same host. **The packaged NSIS build is the only place a CSP mistake actually shows up**; check there before shipping.
- **The app must work with no network** — telemetry is UDP and the TTS weights are bundled, so a race weekend never needs the internet. Everything the UI needs at startup is therefore vendored: UI fonts in `public/fonts/` (see `scripts/fetch-fonts.mjs`), ORT wasm in `public/ort/`, Kokoro weights in `public/kokoro/` (the last two are stripped from the Android bundle, which uses platform TTS). Don't add a render-blocking remote `<link>`/`<script>` to `index.html` — an offline launch stalls on it until it times out. Four network calls remain, all optional and all failing soft: OpenRouter (coaching), the GitHub release check, the Kokoro CDN fallback in dev, and the leaderboards. The leaderboard's Dashboard card is the one that renders on the default tab at every launch — it fires post-paint, times out, and renders nothing on any failure. Keep it that way.
- **The T-Cam's source models live in `assets-src/car-models/`, gitignored, and must stay out of `public/`.** Anything under `public/` is copied verbatim by Vite into `dist/` and from there into the NSIS installer, so keeping ~49 MB of .blend/.c4d/.fbx/.obj there bloated every build for no runtime benefit — only the three derived files (`tcam-ego.png`, `tcam-ego-mask.png`, `tcam-car.glb`) are needed at runtime, and those *are* committed. A fresh clone therefore builds and runs fine but cannot re-bake: `scripts/render-tcam-ego.py` exits with an explanation. Set `F1_COACH_MODELS` to keep the models anywhere else.
- **The T-Cam car model's licence is unknown.** `Formula 2 Car High Poly.blend` arrived with no readme and is now baked into three shipping assets. Establish its terms before a public release. (The two F1 models beside it were rejected: one carries a full Ferrari livery with live trademarks and mirrored UVs, the other floats off the ground and ships a studio backdrop.)
- **The leaderboard's public Supabase anon key is committed** in `lib/leaderboard/config.js` and that is correct — it is scoped entirely by row-level security (public read, zero write) and an env var that goes missing would just fail at runtime with a confusing error. The **service role key is a real secret** and appears nowhere in this repo; Edge Functions read it from their own environment.
- `vite.config.js` excludes `kokoro-js` and `@huggingface/transformers` from `optimizeDeps` — pre-bundling breaks their wasm/worker asset URLs. Don't remove that.
- Keep the version in `package.json` and `tauri.conf.json` in sync — Vite inlines it as `__APP_VERSION__` for the GitHub-release update check (`lib/updateCheck.js`).
